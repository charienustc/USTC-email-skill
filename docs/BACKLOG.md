# 待办

更新于 2026-10-07。这里保留**尚未验收的行为**与**未做的功能**；"测试通过"不等于真机验收完成。

## 待验收：macOS 钥匙串的残余情形

**三个平台现在都真机验过了**：Windows（本机）、Linux（WSL + CI）、macOS（CI）。macOS 第一轮就抓到一个真 bug：

> `security find-generic-password -w` 对**含非 ASCII 字节**的密码打印的是**十六进制转储**，不是文本。存进去的 JSON 里只要有中文授权码，读回来就 `JSON.parse` 失败。

USTC 的授权码通常全是 ASCII，所以这个缺陷只在非 ASCII 时出现——**正因如此它一直没被发现**，直到 macOS runner 第一次把它跑出来。现在存的是 base64（对任何输入都是纯 ASCII），旧格式仍能读回。这正是"必须真机验证"的例证：单元测试和 Linux 都证明不了 `security` 的输出格式。

修完之后 macOS 的真实往返全部通过，包括非 ASCII 密码、加载器偏好、以及"第二次写入是替换而非新增"。

**仍然没覆盖的**：**锁着的钥匙串**（CI 里先跑了 `security unlock-keychain`，所以这条路径没验过）；`commandExists('security', ['help'])` 是否会打开分页器；无人值守环境下 `security` 的 GUI 授权框行为。

验收方法：`.github/workflows/keychain-verification.yml` 的 `macos` job（在 Actions 页手动触发），或在一台 Mac 上跑 `node test/check-credentials.mjs`。

### Linux 的验证结论（2026-10-07）

在 WSL Ubuntu 24.04 上用**免 sudo** 的方式装出 Node 22 与 `secret-tool`，两种情形各跑一遍完整凭据套件：

| 情形 | 结果 |
| --- | --- |
| `secret-tool` 存在、**没有** Secret Service 守护进程 | 34 项全过。套件检测到"存在但不可用"，跳过往返检查，转而验证回退：凭据落进 600 文件、来源诚实报告为文件而不是冒充钥匙串 |
| `gnome-keyring-daemon` 起在私有 session bus 上（真实 Secret Service） | **38 项全过**，含钥匙串往返、加载器偏好、以及"第二次写入是替换而非新增" |

Linux 上曾有过一个真缺陷，就是这一轮发现的：可用性探测只看 `secret-tool` 二进制在不在，于是 headless 机器上后端自称可用、写入时抛错，**用户存不了凭据**。现已改为写入失败退回文件。

## 待验收：真实 IMAP 服务器的边界行为

假服务器证明不了 Coremail 接受什么。以下只在真实邮箱上验证过一部分：

- **超大 literal 与不结束的行**：客户端有 8 MiB / 1 MiB 上限并能报 `IMAP_PROTOCOL`，但**没有在真实服务器上触发过**（构造不出来，也不该构造）。
- **`--preview` 的字节预算**：只在小样本上验证。HTML 邮件或高比例转义时片段会短于请求字符数，这一点的**实际影响范围没有系统性测过**。
- **日期边界**：`--before` 不含当天已实测；但**服务器时区与本地不一致时边界日差一天**的情况没有跨日期实测过。
- **`已发送` / `垃圾邮件` 的搜索**：文件夹能打开已实测，但在这些文件夹里做**中文搜索**没有逐个验证。

## 待验收：附件与批量读取的边界

**机制已验证，规模未验证。** 分块拼接、跨块转义、上限拒绝、批量默认值都已经有断言或真机数据；剩下的是"这台机器的邮箱里根本没有那么大的邮件可测"。

- **接近 25 MiB 的真实附件**：分块路径用 3 MiB + 12345 字节的随机数据（跨 5 块）证明了字节无损，但**没有真实邮件能把这个路径推到上限**。最新 100 封里最大的附件只有 650 KB，连一块都不到——也就是说分块逻辑在日常邮件里几乎不会被触发，它是为大文件准备的保险。25 MiB 附近的性能与内存表现**没有实测过**。
- **单次总量 60 MiB 上限**：只在代码里，**没有测试覆盖**。要触发它需要一封带 10 个 7 MiB 附件的邮件，夹具代价太大。上限本身的算术是对的，但没跑过。
- **Windows 保留名与超长名**：18 种恶意名字在单元测试里全部挡住，但**真实邮件里从未遇到**。真实遇到的中文括号、空格、数字、多重点号（`【T3出行-63.46元-3个行程】…pdf`）都正确保留。
- **quoted-printable 编码的真实附件**：跨块转义（`=41` 与软换行各跨一次块边界）已有断言；**但真实邮箱里没有 QP 编码的附件样本**，全是 base64。

## 已完成

- ✅ **只读技能**：`list` / `search` / `read`，`EXAMINE` + `BODY.PEEK`，真机验证读未读邮件后仍未读。
- ✅ **中文搜索**：`CHARSET UTF-8` + literal，被 Coremail 正确接受。
- ✅ **正文与附件清单**：HTML-only 邮件转纯文本；中文附件文件名正确解码。
- ✅ **`--preview` 汇总**：在同一条连接里附正文片段。实测 5 封提速 5.1 倍；28 封汇总一条连接 934 ms。
- ✅ **skill 路由规则**：明令禁止用 `list --limit 100` 代替 `search`、禁止逐封 `read` 试探；写入成本模型。
- ✅ **凭据跨平台**：三个平台的钥匙串 + 权限 600 文件兜底；`--show` / `--remove` / `--secret-stdin`。
- ✅ **录入工具**：关回显、保存前校验账号格式、保存后验证登录；非 TTY 时给出明确指引。
- ✅ **可移植包**：自带代码、自己定位目录；测试断言包内无绝对路径、无平台绑定文件。
- ✅ **保存附件**：`attach` 把附件写进指定目录，文件名一律重建（路径穿越、Windows 保留名、控制字符、超长名全部挡住），单件 25 MiB / 单次 60 MiB。真机存出的 .xlsx 解压后结构完整，二进制无损。
- ✅ **一次读多封**：`read` 接多个 uid，**一条连接**读完，最多 20 个；找不到的 uid 单独列出不拖垮整批。实测 2 封 784 ms（分两次读 1383 ms）；10 封 **106 ms**。
- ✅ **附件分块与编码的边界**：3 MiB + 12345 字节随机数据跨 5 块拼接**逐字节一致**；quoted-printable 的 `=41` 与软换行**各跨一次块边界**仍正确解码；超过 25 MiB 的部件在**取第一个字节之前**就被拒绝。真实邮件里 2 个 PDF（头尾齐全）、1 个 XML、1 个 OFD/ZIP 全部结构完好。
- ✅ **搜正文**：`--body` 搜正文、`--anywhere` 一次搜"主题或正文"（IMAP 的 `OR`）。探测先说清楚了 `TEXT` 不能用：它慢 50–100 倍**而且结果不一致**（同一词 `SUBJECT`∪`BODY` 有 48 封，`TEXT` 只给 36 封，漏 14 个、另有 2 个在并集之外）。详见 [VERIFICATION](VERIFICATION.md)。
- ✅ **安全审计**：见 [SECURITY-AUDIT-2026-10-06.md](SECURITY-AUDIT-2026-10-06.md)。
